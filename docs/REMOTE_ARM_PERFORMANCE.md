### 指标含义与局限

- CPU 秒是 **estimator 进程全部线程**的用户态+内核态 CPU 时间，不包含播放器和 Python 观察者；一个核满载为 100%。
- P95 延迟是观察者收到对应图像至收到优化里程计的单调时钟差，包含处理排队及初始化，**不是飞控闭环延迟**，也不是仅求解耗时。
- `received_images` 是观察者收到的图像，不证明估计器处理了全部帧。必须结合输出数、输出间隔、覆盖时长、队列溢出日志与误差判断。
- RMSE 使用 bag 内 Vicon `TransformStamped` 的 header 时间插值，位置进行 SE(3) 刚体对齐，**不拟合尺度和时间偏移**。超过 100 ms 的 Vicon 空洞不插值。
- 这里比较的是 **VINS IMU 原点与 bag 内 Vicon 刚体原点的位置**，没有另行应用 Vicon 标记到 IMU 的外参，也没有使用官方 `state_groundtruth_estimate0`；不能等同于官方 EuRoC ATE 排行榜结果。
- 多线程调度和 Ceres 墙钟时间预算使 ARM 重复回放可能有差异；单次测量不构成统计显著性结论。
- 单目相机周期约 **50 ms**；默认后端 `freq: 10` 的输出目标周期是 **100 ms**，两者不能混淆。

关键点：

- `flow_back=0` 不是“更快”，而是直接不产生里程计；不要用它降低 CPU。
- 只缩小队列并不够。默认 max200 的处理时间仍超过 1 s，q1 只是把“排队等待”变成“丢弃旧帧”，延迟仍受单帧处理时间限制；必须先把每帧处理时间降到约 200 ms 以内。

- rate1.5 的 30 Hz 输入压力下，P50/P95 仍约 176/214 ms，但输出从 10 Hz 降到约 7.7 Hz；这是“延迟有界、吞吐下降”的降级，不是全帧实时处理。
- `freq20` 与 `rate1.5` 两次的首输出均为 5.70 s，输出跨度分别为 108.25 s 与 108.20 s；`freq20` 的输出率约 12.2 Hz，说明它增加了后端发布数，却没有改善尾延迟。

## 结论与建议

### 已找到的有效方案

建议作为**显式可选 profile**，而不是静默覆盖默认值：

- `max_cnt: 100`
- `max_solver_time: 0.02`
- `tracking_queue_size: 1`
- `opencv_threads: 1`
- `flow_back: 1`
- `freq: 10`
- `max_num_iterations: 8`

该组合在 EuRoC 20 Hz mono8 回放上的实测：

- easy：P50/P95 约 177/210–215 ms，CPU 202.6–203.6 s，重复性良好；
- medium：P50/P95 约 167/206 ms，CPU 198.7 s，RMSE 与默认相当，首输出提前约 3.6 s；
- difficult：P50/P95 约 151/187 ms，CPU 175.3 s，首输出从 41.9 s 提前到 6.6 s，覆盖从 74.85 s 增至 110.15 s；
- 三者稳态 P95 为 184–212 ms，稳态 P99 为 204–227 ms（medium 有一个 388 ms 的稳态尖峰）。

它的代价是 **按设计丢弃过期图像**：q1 下约一半的 20 Hz 图像不会进入跟踪；30 Hz 输入压力测试中输出降到约 7.7 Hz。下游控制器必须能接受不规则、可能跳变的测量；不能把它描述成“全帧处理”。

### 不推荐的方案

- `flow_back=0`：完全未初始化，0 输出。
- `opencv_threads=2`：CPU 更高，P95 没有实质改善。
- `max120`/`max150`/仅 `max100`：仍为 0.4–1.4 s 量级。
- 仅 `tracking_queue_size=1`：默认单帧处理时间太长，q1 单独无效。
- `freq=20`：CPU 升至 218 s，稳态 P95 反而升到 225 ms。
- 5 Hz 作为默认：difficult 后半段 RMSE 0.762 m，明显不可接受。
- `backend queue=2`：P95 约 540 ms 且精度下降。

### 生产落地边界

1. 本测试是 752×480、约 20 Hz 的 mono8 bag，**不包含**实机 1280×960、30 Hz、MJPEG 解码、相机驱动、飞控桥接、规划控制等负载。不能据此外推实机实时性或飞行安全。
2. 若要采用 q1，建议在 `vins.launch.py` 增加显式 `tracking_queue_size` launch argument（默认仍为 5），由实机启动文件 opt-in；先在 1280×960/30 Hz 实流上单独测量 VINS 的 CPU、P50/P95/P99、输出间隔、特征跟踪和规划输入，再做飞行回归。
3. `max_cnt=100`、`max_solver_time=0.02`、`freq=5` 都应作为独立优化 profile 做实机 A/B，不要直接改 `nav_bringup/config/reality/node_parms.yaml` 或实机标定。
4. 如果实机 1280×960/30 Hz 下仍超过算力，优先考虑把 VINS 外置到更强算力设备，或显式降低分辨率/帧率并重新标定；不要把 q1 当作绕过算力不足的万能开关。
5. `Estimator::failureDetection()` 当前开头直接 `return false`，因此 `failure_reboots=0` 不能证明未发散；本次也没有做故障注入或重启测试。
